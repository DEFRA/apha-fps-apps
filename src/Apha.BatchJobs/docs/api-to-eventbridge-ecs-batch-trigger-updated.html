BatchJobs Worker and PACT API Interface Contract

Canonical single-document handoff for architecture, integration, and stakeholder briefings. This document defines API contract, state transitions, responsibilities, and failure scenarios.

Owner: Batch Worker Architecture Integration: PACT API Last Updated: 2026-06-04

1. Scope and Principles

  • PACT API is the trigger and query surface for PACT-routed jobs.
  • Formal cross-team dispatch contract is EventBridge (not LocalProcess mode).
  • BatchJobs DB is the source of truth for execution outcomes.
  • Trigger store (Redis or memory) is a startup-tracking cache, not the final business state.
  • Single-execution safety is enforced by distributed lock in BatchJobs DB.
  • External correlation key is jobExecutionId and must be used for status polling and cancellation.

Contract boundary: EventBridge dispatch is the supported integration path for PACT API in shared environments. LocalProcess dispatch exists only for development/local debugging and is not part of the inter-team production contract.

2. API Endpoints Required

Method Path Purpose Owner
GET /health API liveness endpoint. PACT API
GET /api/v1/batch-jobs/catalog Returns routable jobs and whether trigger is allowed via PACT API. PACT API
POST /api/v1/batch-jobs/trigger Creates new trigger attempt and dispatches to EventBridge. PACT API
GET /api/v1/batch-jobs/{jobName}/can-run Advisory pre-check for lock and active execution before trigger attempt. PACT API + BatchJobs DB
GET /api/v1/batch-jobs/{jobName}/status Returns correlated status from BatchJobs DB with startup watchdog fallback. PACT API + BatchJobs DB + Trigger store
POST /api/v1/batch-jobs/{jobName}/cancel Creates idempotent durable cancellation request and optionally kills local process in Local/Dev. PACT API + BatchJobs DB

Contract routes are versioned under /api/v{version} and currently served as /api/v1. PACT consumers should call /api/v1 paths.

3. Request and Response Contract

3.1 Trigger

{
  "jobName": "RecreateSummaries",
  "requestedBy": "pact.user@defra.gov.uk"
}
Field Direction Required Contract Rule
jobName Request Yes Must be routable via PACT policy. PACT-routed jobs include RecreateSummaries; HealthCheck is neutral.
requestedBy Request Yes Mandatory caller identity for audit and traceability. Request is rejected if missing or blank.
jobExecutionId Response Always returned Generated by API at trigger acceptance. Caller must persist and use this value for status and cancel operations.
acceptedAtUtc Response Always returned Generated by API at acceptance; used by startup watchdog projection window.
runMode Internal Not caller supplied PACT trigger path dispatches Manual run mode internally; clients do not send runMode.

Trigger success response (202 Accepted):

{
  "accepted": true,
  "source": "pact.api",
  "jobName": "RecreateSummaries",
  "jobExecutionId": "f6ab2d5f8f6849d89b8b5ca73d4f0f17",
  "eventId": "aws-event-id",
  "status": "TriggerAccepted",
  "acceptedAtUtc": "2026-06-04T11:00:00Z",
  "message": "Trigger accepted for dispatch."
}

Local debug responses may include worker process details, but those fields are not part of the production API contract.

Trigger dispatch failure response (503 Service Unavailable):

{
  "accepted": false,
  "source": "pact.api",
  "jobName": "RecreateSummaries",
  "reason": "DispatchFailed"
}

3.2 Cancel

{
  "jobExecutionId": "f6ab2d5f-8f68-49d8-9b8b-5ca73d4f0f17",
  "requestedBy": "pact.user@defra.gov.uk"
}

Cancel outcomes:

  • Accepted: new durable cancel request created.
  • AlreadyRequested: idempotent duplicate request.
  • NoOpTerminal: execution already terminal (Completed, Failed, Cancelled, Skipped).

3.3 Status Query

Recommended query:

GET /api/v1/batch-jobs/{jobName}/status?jobExecutionId={guid}

Status by jobExecutionId is the deterministic contract for user-facing tracking. Latest-by-job-name is convenience/debug fallback and should not be used by PACT UI for deterministic execution tracking.

4. State Model and Transition Contract

4.1 Business States (source of truth: BatchJobs DB)

State Meaning Transition Owner
PendingExecution accepted and queued internally.Worker orchestration
RunningJob currently executing.Worker orchestration
RetryInternal operational retry signal.Worker orchestration
CompletedExecution finished successfully.Worker orchestration
FailedExecution ended with non-cancelled failure.Worker orchestration
CancelledExecution cooperatively or forcibly cancelled.Worker orchestration / cancellation flow
SkippedRun skipped because lock already held by concurrent execution.Worker orchestration

4.2 Startup Watchdog Projection States (PACT API owned projection)

Projected State When used
TriggerAcceptedTrigger recorded, worker not yet confirmed started.
WorkerProcessStartedWorker startup confirmed but no DB execution row yet.
StartFailedTimeoutStartup SLA passed and worker did not reach expected started signal.
WorkerProcessExitedWorker exited before durable execution state available.

Startup watchdog does not declare transport delivery exhaustion. That confirmation belongs to integration transport reconciliation. startupDeadlineUtc and startupSlaSeconds are included in status projection for explicit timeout interpretation.

6. Scenario Coverage (Happy to Worst)

Scenario Expected Behavior
Happy path trigger and run Trigger accepted, worker starts, DB states progress to Completed.
Concurrent trigger while lock active New run is skipped or rejected by can-run checks and lock protections.
EventBridge publish fails before acceptance Trigger returns DispatchFailed (503) and no accepted execution should be treated as active.
EventBridge accepts but worker does not start Status remains startup projection until startupDeadlineUtc, then StartFailedTimeout.
Wrong API route for job name Trigger returns conflict with routing-policy reason.
Trigger accepted but startup delayed Status returns startupWatchdog projection until DB row exists.
Worker exits before durable state Status projects WorkerProcessExited or mapped terminal projection from exit code.
Cancel before execution row exists Cancel accepted and stored in durable cancellation request table keyed by jobExecutionId; worker applies at earliest checkpoint.
Cancel after already requested AlreadyRequested response; no duplicate side effect.
Cancel after terminal state NoOpTerminal response.
Dependency outage during execution Execution ends Failed (or retry then fail) with error details in DB record.
BatchJobs DB unavailable during status Status endpoint returns dependency failure (503); API should not invent terminal business state.
Cancel requested during non-cancellable step Cancellation remains pending and is applied at the next cooperative cancellation checkpoint.
Worker completes before cancellation is processed Cancellation resolves as NoOpTerminal and final state remains terminal business outcome.

6.1 Trigger Lifecycle Sequence

PACT API receives trigger
-> validates requestedBy and jobName
-> creates jobExecutionId
-> dispatches event to EventBridge
-> records trigger attempt in trigger store (Redis in shared environments)
-> worker starts
-> worker creates/updates durable execution state in BatchJobs DB
-> status switches from startup projection to DB-backed business state

7. Rationale: Watchdog and Redis Cache

Why Startup Watchdog Exists

  • There is a short consistency gap between trigger acceptance and first durable DB execution row.
  • Watchdog gives deterministic status projection in that gap for UI and operations.
  • Watchdog prevents false "lost trigger" assumptions by exposing projection timestamps and deadline.

Why Redis Trigger Store Exists

  • Provides cross-instance shared trigger attempt visibility for distributed API deployments.
  • Allows correlated retrieval by jobExecutionId and latest by job name.
  • Supports startup watchdog continuity across restarts and scale events.
  • Redis is the default production path. Outside production, memory store is allowed unless TriggerStore provider is explicitly configured to Redis.

Dispatch Mode Policy

Environment Dispatch Mode Contract Status
Production EventBridge In contract
Development or Local environments LocalProcess (when explicitly configured) or EventBridge LocalProcess out of contract (debug only)
Local developer machine LocalProcess Out of contract (debug only)

8. Operational Notes

  • Correlation contract: jobExecutionId is external key for trigger, status polling, and cancellation.
  • Requester identity contract: requestedBy is mandatory on trigger/cancel requests; missing or blank values are rejected.
  • can-run contract: advisory pre-check only; final single-execution enforcement is the distributed DB lock in worker orchestration.
  • Status rendering rule: Retry is internal; business UI should show Running during retry.
  • Logging correlation rule: trigger accepted logs include jobExecutionId, jobName, eventId; cancellation accepted logs include jobExecutionId, jobName, requestedBy; status logs include jobName, requested/correlated jobExecutionId, query mode, and sourceOfTruth.
  • Local-only janitor service can kill orphaned local worker processes by metadata and age policy.

9. DevOps and Infra Mandatory Asks (PoC Contract)

The following setup is mandatory for this contract and should be implemented by DevOps/Infra as part of initial environment provisioning. These asks follow existing sibling-repo norms: URL-segment v1 APIs, least-privilege IAM, and explicit environment-variable contracts.

9.2 EventBridge to ECS Mappings (Mandatory)

Worker runtime consumes these environment variables: BATCH_JOB_NAME, BATCH_RUN_MODE, BATCH_JOB_EXECUTION_ID.

Trigger Path Input Path or Fixed Value Container Env Variable Required
Manual/API rule $.detail.jobName BATCH_JOB_NAME Yes
Manual/API rule $.detail.runMode BATCH_RUN_MODE Yes
Manual/API rule $.detail.jobExecutionId BATCH_JOB_EXECUTION_ID Yes
Manual/API rule $.detail.requestedBy BATCH_REQUESTED_BY Recommended
Scheduled rule Fixed per rule (example: MABArchive) BATCH_JOB_NAME Yes
Scheduled rule Fixed value: Scheduled BATCH_RUN_MODE Yes
Scheduled rule $.id (EventBridge event envelope id) BATCH_JOB_EXECUTION_ID Yes

Notes: scheduled rules must provide BATCH_JOB_EXECUTION_ID. In strict execution contract mode, worker startup fails if this value is missing or not a valid GUID.

9.3 IAM and Security Group Norms

  • EventBridge invoke role must have ecs:RunTask scoped to approved worker task definition family and target cluster.
  • EventBridge invoke role must have iam:PassRole scoped only to approved worker task role and execution role.
  • PACT/FPS API task roles that publish events must have events:PutEvents scoped to the approved event bus.
  • API tasks may expose inbound 8080 from ALB; batch worker task should have no inbound listener requirement.
  • Worker outbound should be least-privilege for required dependencies (DB, Redis, HTTPS).

10. Stakeholder Summary

This design separates concerns cleanly: PACT API owns trigger ingress, policy routing, and startup projection; Batch Worker owns execution correctness, distributed lock enforcement, and durable state transitions. Together they provide auditable end-to-end traceability from trigger acceptance to terminal outcome.
