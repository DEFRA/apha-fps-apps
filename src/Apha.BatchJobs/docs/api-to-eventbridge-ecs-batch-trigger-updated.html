Batch Job Triggering Approach Recommendation

Updated recommendation for using EventBridge as the common trigger layer for manual/API-triggered jobs, scheduled jobs, and future file-driven jobs.

Updated decision: The preferred approach is now API → EventBridge → ECS Task. This aligns with the team preference, reduces API-side infrastructure dependency, and creates commonality with scheduled jobs that already use EventBridge to invoke ECS tasks.
Context: The worker/batch application already contains orchestration, locking, logging, execution control, status management, and job-specific execution logic. The decision here is only about the trigger/orchestration entry point.

1. Approach Comparison

Approach Flow Infra Dependency in API Best Use Case Pros Cons / Trade-off Updated Fitment
1. API → ECS RunTask API directly invokes ECS Fargate task using RunTask. Medium. Can be minimized using runtime discovery, but API still remains ECS-aware. Manual / adhoc jobs where immediate ECS task ARN is important. Immediate ECS task creation response, task ARN available immediately, simpler direct debugging. API needs ECS permissions and runtime awareness; some infra dependency remains with API. Not Selected
Good technically, but not aligned to lower API infra dependency goal.
2. API → EventBridge → ECS Task API emits event; EventBridge rule invokes ECS task. Low. API only knows event bus/source/detail type. Manual/API-triggered jobs where infra routing should be owned outside API. API does not know ECS target details; infra owns routing; same model can be used for scheduled jobs. More moving parts; API gets event accepted response, not immediate ECS task ARN. Correlation must be handled explicitly. Recommended
Best fit considering infra-decoupling and common trigger model.
3. S3 Event → EventBridge → ECS Task S3 object/file event triggers ECS task through EventBridge. Very low in API. File-driven batch processing. Good for file arrival automation and future ingestion use cases. Not suitable for user/manual trigger unless S3 is artificially introduced. Future Option
Useful only if a job should be triggered by file arrival.

2. Final Recommendation

Use API → EventBridge → ECS Task as the standard trigger model for manual/API-triggered batch jobs.

2.1 Single-Slide Summary (Presentation Shortcut)

Decision in one line: Keep API as a business-event publisher and move ECS runtime orchestration ownership to infrastructure via EventBridge target configuration.
What to Say in Review Where to Show in This Document
Event-based trigger keeps API simpler and less infra-coupled. Section 8.2.1 (side-by-side code) + 8.2.2 (JSON comparison).
ECS task definition remains stable; infra controls runtime/network routing externally. Section 8.2.2 (task-definition context and RunTask JSON comparison).
Infra team becomes clear authority for EventBridge target, IAM, network, retry, and DLQ. Section 10.5 (infra authority model and IaC-style target JSON).
Result: fewer API redeploys for infra changes and better operational consistency with schedules. Sections 2, 8.2.2, and 10.5.2.

The key reason for this change is that the preferred trade-off is now tilted towards lower API infrastructure dependency and commonality with scheduled jobs. Scheduled jobs already use EventBridge to invoke ECS tasks. By using EventBridge for manual/API triggers as well, both scheduled and manual jobs follow the same operational pattern.

Manual/API-triggered flow UI ↓ PACT API / FPS API ↓ EventBridge PutEvents ↓ EventBridge Rule ↓ ECS RunTask Target ↓ Worker Task ↓ Job Orchestrator ↓ PostgreSQL + CloudWatch
Scheduled job flow EventBridge Schedule / Rule ↓ ECS RunTask Target ↓ Worker Task ↓ Job Orchestrator ↓ PostgreSQL + CloudWatch

6. Job Execution ID and Correlation

Since the API may not touch the database before the worker starts, the API can generate a jobExecutionId itself and include it in the event. This ID becomes the business-level correlation key.

API generates jobExecutionId ↓ API publishes EventBridge event ↓ API returns jobExecutionId to UI ↓ EventBridge invokes ECS worker task ↓ Worker receives jobExecutionId as env variable ↓ Worker creates/updates job status in DB ↓ UI polls status using jobExecutionId

If the UI polls before the worker inserts the row, the status API can return PendingStart / TriggerAccepted for that jobExecutionId.

6.1 JobExecutionId to JobQueueId Flow (Updated)

Clarification: jobExecutionId is API-generated correlation ID. jobQueueId is database/runtime execution row identity from operational.tbljobqueue. Both should be linked once worker starts.

1) API receives trigger request 2) API generates jobExecutionId (GUID) and publishes EventBridge event 3) API returns TriggerAccepted + jobExecutionId to UI 4) Worker starts with BATCH_JOB_EXECUTION_ID=jobExecutionId 5) Worker inserts execution row in operational.tbljobqueue - DB generates jobQueueId (identity/sequence) - Row stores correlation/jobExecutionId 6) Worker and status APIs expose both IDs for traceability 7) UI continues polling by jobExecutionId (stable external key) - API may additionally return jobQueueId once available

6.1.1 Suggested Status Response After Worker Row Exists

{
  "jobExecutionId": "b8f9d4a16bb64a6c97e44e9c2e09f111",
  "jobQueueId": 987654,
  "status": "Running",
  "message": "Worker started and queue record created."
}

6.1.2 Correlation Rule

  • External/UI/API correlation key: jobExecutionId.
  • Internal database/worker key: jobQueueId.
  • Every log line and status payload should include jobExecutionId; include jobQueueId once known.

8.2 API Code - Publish Event

using Amazon.EventBridge;
using Amazon.EventBridge.Model;
using System.Text.Json;

public async Task<string> TriggerBatchJobAsync(
    string jobName,
    string requestedBy,
    CancellationToken cancellationToken = default)
{
    ArgumentException.ThrowIfNullOrWhiteSpace(jobName);

    var jobExecutionId = Guid.NewGuid().ToString("N");

    var detail = JsonSerializer.Serialize(new
    {
        jobExecutionId,
        jobName,
        runMode = "Manual",
        requestedBy,
        requestedAtUtc = DateTime.UtcNow
    });

    var request = new PutEventsRequest
    {
        Entries =
        [
            new PutEventsRequestEntry
            {
                EventBusName = _configuration["EventBridge:EventBusName"] ?? "default",
                Source = _configuration["EventBridge:Source"] ?? "fps.api",
                DetailType = _configuration["EventBridge:DetailType"] ?? "BatchJob.TriggerRequested",
                Detail = detail
            }
        ]
    };

    var response = await _eventBridge.PutEventsAsync(request, cancellationToken);

    if (response.FailedEntryCount > 0)
    {
        var failureText = string.Join("; ", response.Entries
            .Where(e => !string.IsNullOrWhiteSpace(e.ErrorCode))
            .Select(e => $"{e.ErrorCode}: {e.ErrorMessage}"));

        throw new InvalidOperationException($"Failed to publish batch trigger event. {failureText}");
    }

    return jobExecutionId;
}

8.2.1 Side-by-Side Code: Event Publish vs Direct ECS RunTask

Why this comparison matters: both snippets can trigger the worker, but the EventBridge producer code is smaller, cleaner, and avoids hardcoding ECS runtime/network details in the API.

Option A (Recommended): API publishes EventBridge event

using Amazon.EventBridge;
using Amazon.EventBridge.Model;
using System.Text.Json;

public async Task<string> TriggerViaEventAsync(string jobName, string requestedBy)
{
    var jobExecutionId = Guid.NewGuid().ToString("N");

    var detail = JsonSerializer.Serialize(new
    {
        jobExecutionId,
        jobName,
        runMode = "Manual",
        requestedBy,
        requestedAtUtc = DateTime.UtcNow
    });

    await _eventBridge.PutEventsAsync(new PutEventsRequest
    {
        Entries =
        [
            new PutEventsRequestEntry
            {
                EventBusName = _configuration["EventBridge:EventBusName"] ?? "default",
                Source = "fps.api",
                DetailType = "BatchJob.TriggerRequested",
                Detail = detail
            }
        ]
    });

    return jobExecutionId;
}

Option B (Direct): API calls ECS RunTask

using Amazon.ECS;
using Amazon.ECS.Model;

public async Task<string> TriggerViaEcsAsync(string jobName, string requestedBy)
{
    var jobExecutionId = Guid.NewGuid().ToString("N");

    var response = await _ecs.RunTaskAsync(new RunTaskRequest
    {
        Cluster = _configuration["Ecs:ClusterArn"],
        TaskDefinition = _configuration["Ecs:TaskDefinitionArn"],
        LaunchType = LaunchType.FARGATE,
        NetworkConfiguration = new NetworkConfiguration
        {
            AwsvpcConfiguration = new AwsVpcConfiguration
            {
                Subnets = _configuration.GetSection("Ecs:Subnets").Get<List<string>>()!,
                SecurityGroups = _configuration.GetSection("Ecs:SecurityGroups").Get<List<string>>()!,
                AssignPublicIp = AssignPublicIp.DISABLED
            }
        },
        Overrides = new TaskOverride
        {
            ContainerOverrides =
            [
                new ContainerOverride
                {
                    Name = _configuration["Ecs:ContainerName"],
                    Environment =
                    [
                        new KeyValuePair { Name = "BATCH_JOB_EXECUTION_ID", Value = jobExecutionId },
                        new KeyValuePair { Name = "BATCH_JOB_NAME", Value = jobName },
                        new KeyValuePair { Name = "BATCH_RUN_MODE", Value = "Manual" },
                        new KeyValuePair { Name = "BATCH_REQUESTED_BY", Value = requestedBy }
                    ]
                }
            ]
        }
    });

    return response.Tasks.First().TaskArn;
}
What API Must Know Event Publish (Recommended) Direct ECS RunTask
Config footprint in API Small: event bus + source + detail type. Large: cluster ARN, task definition ARN, container name, subnets, security groups, launch settings.
IAM needed by API events:PutEvents only. ecs:RunTask + iam:PassRole (+ broader ECS runtime awareness).
Ownership model Infra owns routing and ECS target details in EventBridge. API must carry and maintain infra/runtime coupling.
Operational commonality Same trigger layer as scheduled jobs (EventBridge). Separate trigger path from scheduled model.
Conclusion from code and config: calling via EventBridge is simpler at the API boundary and materially less infra-dependent. API remains a producer of business events, while infrastructure owns execution routing to ECS.

8.4 Publish Reliability and Failure Contract

The API publish path uses bounded retry for transient EventBridge ingress failures and returns a deterministic 503 payload when publish is not accepted.

Behavior Current Contract
Transient publish handling Up to 3 attempts with exponential backoff and jitter for throttling/timeout/5xx style failures.
Request cancellation Cancellation token is respected and operation exits immediately when caller cancels.
Publish failure response API returns 503 ServiceUnavailable with machine-readable reasonCode.

8.4.1 503 Response Shape (Publish Not Accepted)

{
  "accepted": false,
  "publishAccepted": false,
  "reason": "Event publish failed",
  "reasonCode": "PublishTransientFailedAfterRetry",
  "jobName": "FECProcess",
  "jobExecutionId": "b8f9d4a16bb64a6c97e44e9c2e09f111",
  "message": "Unable to publish trigger event to EventBridge. Please retry."
}

8.4.2 reasonCode Values

reasonCode Meaning Client Action
PublishTransientFailedAfterRetry Transient publish issues persisted after bounded retries. Retry operation from UI/client.
PublishNonRetryableFailed Non-transient publish failure was returned by AWS SDK/EventBridge path. Do not auto-retry repeatedly; surface error and investigate.
PublishConfigurationInvalid Required EventBridge API configuration is missing/invalid. Fix API configuration before retrying.
PublishInvalidResponse EventBridge response shape was invalid (for example, missing entry/event id). Retry once, then investigate service/runtime logs.

8.5 Implemented Polling Endpoint for Option 2 (No New Lifecycle Table)

To avoid indefinite PendingStart without adding a new API lifecycle table, the API exposes an inference endpoint that combines:

  • jobExecutionId (from trigger response)
  • acceptedAtUtc (from trigger response)
  • Execution existence check in operational.tbljobqueue
  • Timeout rule: acceptedAtUtc + timeoutSeconds + bufferSeconds
GET /api/batch-jobs/triggers/{jobExecutionId}/startup-status
    ?acceptedAtUtc=2026-05-08T10:12:30Z
    &timeoutSeconds=3600
    &bufferSeconds=120

Returned status is one of:

  • PendingStart (no queue row yet, still within timeout window)
  • StartFailedTimeoutLikely (no queue row after timeout window)
  • Running / Completed / Failed (queue row exists and worker status observed)
Current option-2 caveat: API does not programmatically query DLQ. StartFailedTimeoutLikely is an inference based on timeout + missing execution row, while DLQ alarms/operations remain infra-driven.

8.6 Failure Handling Approach (Publish Side vs ECS Startup)

Failure Point Detection API/Infra Response UI/Client Contract
Publish failure before EventBridge acceptance PutEvents exception or failed entry from AWS SDK. API retries bounded (3 attempts). On final failure returns 503 + reasonCode. Treat as not accepted; safe to retry trigger with same business intent.
Event accepted but ECS task/container does not start No execution row by startup deadline and/or DLQ signal from exhausted EventBridge target retries. Mark lifecycle as StartFailedTimeout (inferred) or StartFailedDeliveryExhausted (DLQ confirmed). Show startup failure state; allow retry and surface operator guidance.
Container started but application crashed early ECS task stop reason + worker logs + status row transitions. Status transitions to Failed with failure metadata persisted for troubleshooting. Show execution failed after start (not publish failure).

8.6.1 Recommended Retry Semantics

  • Publish-side failure: API-level retry only, because EventBridge never accepted the event.
  • Post-accept delivery failure: EventBridge target retry + DLQ path only, not API retry loop.
  • Startup timeout: one user/client retrigger action after deadline; avoid aggressive automatic retrigger storms.

8.6.2 Compact Failure Sequence (Review-Friendly)

Failure Path A: Publish-side failure (before EventBridge acceptance) UI -> API Trigger Endpoint -> PutEvents attempt #1/#2/#3 -> still failed -> API returns 503 + reasonCode=PublishTransientFailedAfterRetry -> UI shows "Not accepted" and offers retry Failure Path B: Event accepted, but ECS container fails to start UI -> API Trigger Endpoint -> PutEvents accepted (TriggerAccepted + jobExecutionId) -> EventBridge Rule/Target invokes ECS -> ECS startup fails (image pull/IAM/network/capacity) -> no worker-start signal by startupDeadlineUtc -> API projects StartFailedTimeout -> if DLQ evidence arrives: project StartFailedDeliveryExhausted -> UI shows startup failure with retry + operator diagnostics

Presenter tip: emphasize that Path A is producer-boundary reliability (API retries), while Path B is post-accept delivery reliability (EventBridge retry/DLQ + startup deadline projection).

11.1 Configured Reliability Boundaries

Boundary Configured Setting Intent
API → EventBridge ingress API-side bounded transient retry: maxAttempts=3, exponential backoff + jitter. Handle throttling/timeouts/5xx before event acceptance.
EventBridge Rule → ECS target Retry policy: MaximumRetryAttempts=24, MaximumEventAgeInSeconds=3600. Handle transient target invocation failures after EventBridge has accepted the event.
EventBridge Rule → DLQ DeadLetterConfig enabled to SQS DLQ (for example batch-trigger-dlq). Capture events that could not be delivered to ECS target within retry window.
API failure response contract 503 with deterministic reasonCode. Allow UI/client to decide retry vs operator action consistently.
Important boundary rule: EventBridge target retry/DLQ only applies after EventBridge accepts the event. If PutEvents fails at API ingress, only API-side retry/handling applies.

11.2 End-to-End Sequence (Manual Trigger)

1) User triggers job from UI. 2) API validates request and running-state guard (400/404/409 paths if invalid). 3) API generates jobExecutionId. 4) API calls PutEvents to EventBridge. - If ingress transient failure: API retries up to 3 attempts. - If still failed: API returns 503 with reasonCode. 5) EventBridge accepts event and matches rule. 6) EventBridge invokes ECS RunTask target. - If target invocation transiently fails: EventBridge retries per policy. - If retries exhaust or event age exceeded: Event pushed to DLQ. 7) Worker container starts, reads env overrides. 8) API-side lifecycle tracker marks startup observed and projects Running based on worker/runtime signals. 9) Worker writes execution outcomes (Running/Completed/Failed) and logs with jobExecutionId. 10) UI polls its own API and renders lifecycle + execution state.

11.3 Scenario Matrix and Handling

Scenario Where It Fails Observed Signal Handling
Invalid request or unknown job API validation/status guard 400 / 404 Client corrects request; no EventBridge call is made.
Job already running API status guard 409 Conflict Client waits/polls current execution; prevent duplicate start.
Ingress transient publish failure API → EventBridge PutEvents API warning logs with retry attempts Automatic API retry (3 attempts).
Ingress transient failure after retries API → EventBridge PutEvents 503 + reasonCode=PublishTransientFailedAfterRetry UI/client can safely retry trigger.
Ingress non-retryable publish failure API → EventBridge PutEvents 503 + reasonCode=PublishNonRetryableFailed Escalate to operator; verify AWS/EventBridge response and config.
API EventBridge config missing/invalid API configuration 503 + reasonCode=PublishConfigurationInvalid Fix API settings and redeploy/reload config.
EventBridge accepted but target invoke transiently fails EventBridge Rule → ECS target EventBridge target failure metrics/logs Automatic EventBridge target retries per policy.
ECS container failed to start (image pull/IAM/network/capacity) ECS startup/runtime after target invoke No running worker signal, ECS stopped-task reason, possible timeout or DLQ follow-on Project StartFailedTimeout (deadline) or StartFailedDeliveryExhausted (DLQ confirmed); surface retry + operator diagnostics.
Target retries exhausted / event too old EventBridge Rule → ECS target Message in DLQ Operate from DLQ: inspect payload, fix cause, replay or retrigger.

11.4 DLQ Operational Handling

  1. Monitor DLQ depth and EventBridge target failure metrics with alerts.
  2. On DLQ message, inspect jobExecutionId, jobName, and failure reason metadata.
  3. Fix infra/runtime issue (IAM/network/task definition/cluster capacity) before replay.
  4. Replay from DLQ or manually retrigger, ensuring idempotency rules are respected.
  5. Track incident closure with evidence from CloudWatch and status API records.

11.5 Recommended Execution Status Model

This model prevents indefinite PendingStart behavior when EventBridge accepted the event but ECS task launch could not be completed.

Note: This status model is API-side lifecycle projection for each API owner (PACT/FPS). It is not a required change to worker domain enums/entities.

Status Set By When UI Meaning
TriggerAccepted API PutEvents accepted by EventBridge. Request accepted; startup in progress.
PendingStart Status API projection Accepted but worker start signal not yet observed. Still waiting for ECS task start.
Running API projection from worker/runtime signals Worker task starts and startup has been observed/correlated by API. Job actively executing.
Completed API projection from worker/runtime signals Worker finishes successfully and API projects terminal status to UI. Success terminal state.
Failed API projection from worker/runtime signals Worker started but job failed; API projects failure to UI. Execution failed after start.
StartFailedTimeout Reconciler/timeout evaluator No worker start observed before startup SLA deadline. Startup failure; safe to retry trigger.
StartFailedDeliveryExhausted DLQ processor Event landed in DLQ after EventBridge target retries exhausted/age exceeded. Delivery failure; investigate infra and replay/retry.

11.6 Transition Rules (How It Works End-to-End)

Trigger request -> API validates -> if invalid: 400/404/409 terminal response API publishes to EventBridge -> if ingress failure after API retries: 503 with reasonCode (no accepted execution) -> if accepted: create/update execution as TriggerAccepted with startupDeadlineUtc Polling path before worker starts -> Status API returns PendingStart while nowUtc <= startupDeadlineUtc Worker starts -> API marks startup observed and projects Running -> API projects Completed or Failed based on worker/runtime outcome signals Worker did not start in time -> Timeout evaluator sets StartFailedTimeout EventBridge target delivery exhausted -> DLQ consumer sets StartFailedDeliveryExhausted -> include failure metadata for operations and replay decision

11.7 Suggested Startup SLA and Deadlines

Parameter Suggested Value Rationale
startupDeadlineUtc AcceptedAt + 10 minutes Long enough for transient target retry and ECS startup latency.
Status poll interval 2-5 seconds with client backoff Avoid aggressive API polling while preserving responsiveness.
PendingStart auto-timeout Hard transition at deadline Prevents indefinite spinner behavior in UI.

11.9 Compact State Diagram

[Trigger Request] | +-- API validation fails ---------------------------> [400/404/409] | +-- PutEvents ingress fails after API retries ------> [503 + reasonCode] | +-- PutEvents accepted -----------------------------> [TriggerAccepted] | +--> [PendingStart] | +--> Worker starts ----------> [Running] --> [Completed] | | | +----------> [Failed] | +--> Startup deadline passed -> [StartFailedTimeout] | +--> EventBridge target retries exhausted / DLQ -> [StartFailedDeliveryExhausted]

Operational note: StartFailedDeliveryExhausted is typically set by a DLQ consumer/reconciler that correlates DLQ messages to jobExecutionId.

In this sample's option-2 implementation, the API does not set StartFailedDeliveryExhausted itself because it does not query DLQ programmatically.

13. Key Trade-offs and Mitigations

Trade-off Impact Mitigation
API does not get ECS TaskArn immediately. API cannot prove task started, only that event was accepted. Use jobExecutionId as business tracking ID. Worker updates DB when it starts.
More moving parts than direct RunTask. EventBridge rule/target needs infra setup. Standardize Terraform/CloudFormation module for scheduled and manual jobs.
Correlation is indirect. Need to trace API → EventBridge → ECS → Worker logs. Pass BATCH_JOB_EXECUTION_ID and include it in every log/status update.
Event delivery failure is asynchronous. Failure may not be visible to API immediately. Configure EventBridge retry and DLQ; monitor DLQ and EventBridge metrics.
Ingress publish can fail before EventBridge accepts event. Target retry/DLQ does not apply for pre-accept failures. Handle at producer boundary with bounded retry and deterministic 503 + reasonCode.

14. Final Design Summary

Final direction: Use EventBridge as the common trigger layer for API/manual jobs and scheduled jobs, with ECS Fargate as the worker execution runtime.
PACT API / FPS API → PutEvents only → No ECS cluster/subnet/security group config in API EventBridge → Owns routing → Owns ECS target setup → Passes job details to worker using container overrides Worker Task → Reads BATCH_JOB_NAME, BATCH_RUN_MODE, BATCH_JOB_EXECUTION_ID → Executes existing orchestration → Updates status/logs → Exits
