# RecreateSummaries — .NET Conversion Plan

**Status date:** 2026-05-11
**Scope:** `sp_RecreateSummaries` orchestration chain (14 child procedures + conditional period refresh)
**Goal:** Exact parity with legacy SQL Server behavior via step-by-step PostgreSQL SQL execution in .NET

---

## Conversion Principles

| Rule | Detail |
|------|--------|
| **No LINQ conversion** | All SQL logic stays as SQL. Do not rewrite queries as LINQ expressions. |
| **No formula redesign** | All calculations are reproduced exactly as written in the legacy procedure. |
| **No optimisation** | No query hints, index changes, or structural improvements until parity is proven. |
| **Move orchestration only** | The only .NET work is sequencing steps, managing the transaction, and the lock-check branch. |
| **PostgreSQL syntax conversion only** | Change SQL Server–specific syntax to PostgreSQL-compatible equivalents (see Phase 4). |
| **Parity first** | The .NET job must produce byte-for-byte equivalent outputs before any refactoring is considered. |
| **year/fpsyear deferred** | The PostgreSQL database will carry a `year`/`fpsyear` column. Deriving and propagating that value from context is a **post-parity** task. For the initial conversion, `year`/`fpsyear` handling follows the legacy procedure exactly — no new column logic is introduced until parity is signed off. |

## Phase 1 — Create One .NET Job Handler

Create `RecreateSummariesJobHandler` in:

```
src/Apha.BatchJobs/Apha.BatchJobs.Application/Jobs/ScheduledJobs/RecreateSummaries/
```

### Input contract

| Parameter | Type | Source |
|-----------|------|--------|
| `Month` | `int` | Caller-supplied (equivalent to legacy `@Month`) |
| `TriggeredBy` | `string` | Calling user identity (replaces `sp_Get_SP_No` / `SYSTEM_USER`) |
| `JobExecutionId` / `RunId` | `string` | Generated by `JobOrchestrator` before handler is invoked |

### Responsibility

Replaces `sp_RecreateSummaries` (parent procedure), whose sole job was ordered execution of child procedures plus a post-execution lock-check branch.

Lock acquisition and release remain owned by `JobOrchestrator`, exactly as the `MabArchiveJobHandler` pattern.

## Phase 4 — SQL Server → PostgreSQL Syntax Conversion

Apply only the following mechanical substitutions. **No formula changes.**

| SQL Server | PostgreSQL |
|------------|------------|
| `ISNULL(x, 0)` | `COALESCE(x, 0)` |
| `GETDATE()` | `CURRENT_TIMESTAMP` |
| `CONVERT(money, expr)` | `CAST(expr AS numeric)` |
| `[ColumnName]` | `columnname` (or `"ColumnName"` if the DB team preserved mixed-case) |
| `dbo.TableName` | `fps.tablename` (or the configured schema) |
| `WHILE` loop | Moved to C# loop in handler; SQL executes the body per iteration |

Any other syntax difference encountered during conversion must be documented in the procedure's `.sql` file header before applying a fix.

## Phase 5 — Transaction Strategy

Use a **single transaction** wrapping steps 1–14 plus the conditional refresh.

```
BEGIN TRANSACTION
  → Step 1:  DeleteFpsTotals
  → Step 2:  CreateFpsTotals
  → Step 3:  InsertMissingProjects
  → Step 4:  DeleteTimeCostCalcs
  → Step 5:  CreateTimeCostCalcs
  → Step 6:  DeleteProjectMonthCasework
  → Step 7:  CreateProjectMonthCasework
  → Step 8:  DeleteProjectMonthFinal
  → Step 9:  DeleteProjectMonth2
  → Step 10: CreateProjectMonthSingle
  → Step 11: DeleteProjectMonth3
  → Step 12: CreateProjectMonthCumulative
  → Step 13: CreateProjectMonthFinal
  → Step 14: LogRecreateSummaries
  → [read periodLocked]
  → if periodLocked = 0:
      → Step 15: RefreshPeriodMo
      → Step 16: RefreshPeriodPsc
      → Step 17: RefreshPeriodTcc
COMMIT
```

On any failure:
```
ROLLBACK
log failed step name + error message
exit with failure result
```

Rationale: preserves the legacy "all-or-nothing" behaviour — a partial rebuild is never left in the database.

## Phase 6 — Lock-Check Logic in .NET

Implement exactly the following after step 14 completes (inside the same transaction):

```csharp
var periodLocked = await GetPeriodLockedAsync(month, cancellationToken);

if (periodLocked == 0)
{
    await ExecuteStepAsync(new RefreshPeriodMoStep(month), cancellationToken);
    await ExecuteStepAsync(new RefreshPeriodPscStep(month), cancellationToken);
    await ExecuteStepAsync(new RefreshPeriodTccStep(month), cancellationToken);
}
```

`GetPeriodLockedAsync` executes:

```sql
-- 15_get_period_locked.sql  (helper query, not a numbered step)
SELECT periodlocked
FROM   fps.tblperiod
WHERE  endperiod = @month;
```

No deviation from legacy logic: when `periodLocked <> 0` the three refresh procedures are silently skipped, exactly as the original `IF @periodLocked = 0` branch.

## Phase 7 — Replace `sp_Get_SP_No`

Legacy `sp_Get_SP_No` extracted the current database login via `SYSTEM_USER` and returned it as `UserID`.

In .NET the triggering user is already available as `TriggeredBy` (supplied by the caller / API layer). Use it directly:

```csharp
// Inside LogRecreateSummariesStep
var userId = context.TriggeredBy;   // no stored-proc call needed
```

`14_log_recreate_summaries.sql` inserts:

```sql
INSERT INTO fps.recreatesummaries_log (userid, period, datadone)
VALUES (@userId, @month, CURRENT_TIMESTAMP);
```

No business impact: the correct triggering user is recorded. The intermediate call to `sp_Get_SP_No` is not reproduced.

## Phase 8 — Step Result Capture & Validation Checklist

### Per-step result record

Every step returns a `StepResult`:

```csharp
public record StepResult(
    string StepName,
    int    RowsAffected,
    DateTime StartTime,
    DateTime EndTime,
    StepStatus Status,          // Success | Failed | Skipped
    string? ErrorMessage
);
```

All results are collected by the handler and included in the job's execution log.

### Post-conversion parity checks

Run the following comparisons between legacy SQL Server output and PostgreSQL/.NET output for the same `@Month` value:

| Check | Required |
|-------|----------|
| Row count per target table after each step | Yes |
| `SUM` of money/cost columns per target table | Yes |
| Month-scoped output only (`WHERE endperiod = @month`) | Yes |
| Locked period: steps 15–17 **not** executed, no rows changed in period tables | Yes |
| Unlocked period: steps 15–17 **executed**, row counts match legacy | Yes |
| `recreatesummaries_log` insert: correct `userid`, `period`, `datadone` | Yes |

Each check must be signed off before the job is considered production-ready.

---

## Implementation Rule

> **First conversion target = parity, not improvement.**
>
> Once `RecreateSummariesJobHandler` produces exactly the same outputs as the legacy SQL Server execution for the same input month, and all validation checks pass, only then consider refactoring, optimisation, or step decomposition.
>
> **year/fpsyear column (post-parity work):** The new PostgreSQL schema includes a `year`/`fpsyear` column. Deriving this value from context (e.g. `IExecutionYearContext`) and writing it into the relevant tables is a separate, follow-on task. It must not be introduced during the parity conversion — doing so would change outputs and make parity comparison impossible. Once parity is confirmed, a dedicated story should cover context-driven `year`/`fpsyear` population.
