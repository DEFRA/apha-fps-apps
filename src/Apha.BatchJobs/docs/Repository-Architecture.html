🎯 Architecture Overview

Design Pattern

Apha.BatchJobs implements a Layered Architecture with clear separation of concerns across five distinct layers:

Architecture Stack

┌─────────────────────────────────────┐
│ Apha.BatchJobs.Api │ ← HTTP Entry Point (Status/Trigger)
├─────────────────────────────────────┤
│ Apha.BatchJobs.Worker │ ← Background Job Orchestration
├─────────────────────────────────────┤
│ Apha.BatchJobs.Application │ ← Business Logic & Use Cases
├─────────────────────────────────────┤
│ Apha.BatchJobs.Domain │ ← Domain Models & Entities
├─────────────────────────────────────┤
│ Apha.BatchJobs.Infrastructure │ ← Data Access & External Services
└─────────────────────────────────────┘

Unique Characteristics

  • Dual Entry Points: Both HTTP API and background worker in single solution
  • Domain-Driven: Emphasizes domain models over data models
  • Shared Application Logic: API and Worker both consume Application layer
  • Infrastructure Abstraction: Persistence implementation hidden behind interfaces
  • Consolidated Tests: Single UnitTests project covering all layers

📦 Project Breakdown

1. Entry Points (Dual Interface)

🌐 Apha.BatchJobs.Api

Entry Point: HTTP ASP.NET Core REST Endpoints

Purpose: Exposes HTTP endpoints for triggering and monitoring batch jobs

Key Responsibilities
  • Define REST API controllers and routes
  • Request validation and contract mapping
  • Call Application layer use cases
  • Return standardized API responses
  • Implement authentication/authorization
Example Endpoints
POST /api/v1/jobs/trigger - Queue a new job GET /api/v1/jobs/{jobId}/status - Get job execution status GET /api/v1/jobs/history - List recent jobs GET /api/v1/health - Health check endpoint
Dependencies
  • Apha.BatchJobs.Application
  • Apha.Common (shared utilities)
  • ASP.NET Core 10.0

⚙️ Apha.BatchJobs.Worker

Entry Point: Background Service Worker Host Job Orchestration

Purpose: Runs as a background service that dequeues and executes batch jobs

Key Responsibilities
  • Initialize job scheduler/orchestrator
  • Poll for pending jobs from database
  • Execute jobs using Application layer
  • Update job status and completion state
  • Handle retries, failures, and logging
  • Manage graceful shutdown
Run Modes
  • Manual: Execute specific job by name
  • Scheduled: Auto-poll for jobs on timer
  • Health Check: Basic connectivity verification
Dependencies
  • Apha.BatchJobs.Application
  • Apha.Common (shared utilities)
  • Microsoft.Extensions.Hosting (.NET Worker Host)

2. Business Logic Layer

🧠 Apha.BatchJobs.Application

Business Logic Use Cases Orchestration

Purpose: Contains all business logic, use case implementations, and orchestration of domain objects

Key Responsibilities
  • Implement business workflows (e.g., ScheduleJobs, RecreateSummaries)
  • Coordinate between Domain and Infrastructure layers
  • Handle transactions and data consistency
  • Implement application-level services
  • Transform domain objects for API/Worker responses
Typical Structure
  • Services/ - Use case implementations
  • Abstractions/Interfaces/ - Contracts for repositories, external services
  • DTOs/ - Data transfer objects for cross-layer communication
  • Mappers/ - Map between Domain and DTO models
Dependencies
  • Apha.BatchJobs.Domain
  • Apha.Common (shared utilities)

3. Domain Layer

🎲 Apha.BatchJobs.Domain

Domain Models Entities Value Objects

Purpose: Represents the core business domain with entities, value objects, and domain logic

Key Responsibilities
  • Define domain entities (Job, JobExecution, Schedule, etc.)
  • Model business rules and constraints
  • Implement domain-level validation
  • Define repository interfaces (contracts)
  • Define aggregate roots
Typical Entities
  • Job: Represents a batch job definition
  • JobExecution: Represents a single execution run
  • JobSchedule: Defines scheduling parameters
  • BatchContext: Execution context and parameters
Dependencies
  • Apha.Common (shared utilities)
  • .NET Core libraries only

4. Infrastructure Layer

💾 Apha.BatchJobs.Infrastructure

Data Access External Services Implementations

Purpose: Implements repository interfaces, database context, and external service integrations

Key Responsibilities
  • Implement Domain layer repository interfaces
  • Configure Entity Framework Core DbContext
  • Execute database migrations
  • Implement external service clients (if needed)
  • Handle database connection pooling
  • Implement caching layers
Typical Components
  • BatchJobsDbContext: EF Core DbContext for domain entities
  • Repositories/: Repository implementations
  • Migrations/: EF Core migration scripts
  • Configuration/: Entity mapping configuration
  • Services/: External service integrations
Database Technology
  • Database: PostgreSQL 16+
  • ORM: Entity Framework Core 10.0
  • Migrations: EF Code-first
Dependencies
  • Apha.BatchJobs.Domain
  • Apha.Common (shared utilities)
  • Entity Framework Core 10.0
  • Npgsql (PostgreSQL provider)

5. Testing Layer

🧪 Apha.BatchJobs.UnitTests

Unit Tests Integration Tests Consolidated

Purpose: Provides comprehensive test coverage for all layers in single project

Test Organization
  • Domain/ - Domain entity and value object tests
  • Application/ - Use case and service tests
  • Infrastructure/ - Repository and database tests
  • Api/ - Controller and endpoint tests (if isolated)
  • Integration/ - End-to-end workflow tests
Test Approach
  • Unit Tests: Fast, in-memory, no external dependencies
  • Integration Tests: Use real PostgreSQL instance (test db)
  • Mocking: Moq for interface mocking
  • Fixtures: Reusable test data setup
Dependencies
  • All other projects in solution
  • xUnit (test framework)
  • Moq (mocking framework)
  • FluentAssertions (readable assertions)

🚪 Entry Points Detailed

Apha.BatchJobs.Api - HTTP Entry Point

Runs as an ASP.NET Core HTTP service, typically hosted on port 8080.

Startup Flow
  1. Configure dependency injection (API, Application, Infrastructure services)
  2. Configure Entity Framework DbContext with PostgreSQL connection
  3. Wire up middleware pipeline (logging, error handling, authentication)
  4. Map API route handlers
  5. Start HTTP server

Apha.BatchJobs.Worker - Background Job Entry Point

Runs as a .NET Worker Service, continuously polling for jobs.

Startup Flow
  1. Configure dependency injection (Worker, Application, Infrastructure services)
  2. Configure Entity Framework DbContext with PostgreSQL connection
  3. Register background job services and orchestrators
  4. Start hosted services
  5. Begin polling for pending jobs

Deployment Modes

Mode Entry Point Purpose Environment Variables
API Only Apha.BatchJobs.Api HTTP trigger/status service only ASPNETCORE_ENVIRONMENT, Port
Worker Only Apha.BatchJobs.Worker Background job execution only BATCH_JOB_NAME, BATCH_RUN_MODE
Combined Both (separate containers) Full system: HTTP + execution All of above (separately configured)

Important Notes

  • No circular dependencies: Strict one-way dependency flow
  • Domain layer independence: Domain contains no infrastructure code
  • Application layer purity: No direct database access (uses repository interfaces)
  • Infrastructure isolation: Database implementation hidden from higher layers

📐 Coding Conventions

Naming Conventions

  • Interfaces: Prefixed with I (e.g., IJobRepository)
  • Implementations: Suffixed with layer name (e.g., JobRepositoryPostgres)
  • Services: Suffixed with Service (e.g., JobSchedulingService)
  • DTOs: Suffixed with Dto (e.g., JobExecutionDto)
  • Entities: No suffix, plain domain model names (e.g., Job, JobExecution)

Namespace Conventions

Apha.BatchJobs.Api ├── Controllers ├── Middleware └── Startup Apha.BatchJobs.Application ├── Services ├── Abstractions ├── DTOs └── Mappers Apha.BatchJobs.Domain ├── Entities ├── ValueObjects └── Abstractions Apha.BatchJobs.Infrastructure ├── Repositories ├── Data ├── Configuration └── Services

Design Principles

  • Dependency Injection: Constructor injection preferred, field injection avoided
  • Repository Pattern: All data access through repository interfaces
  • Immutability: Value objects should be immutable
  • Single Responsibility: Each class has one reason to change
  • Testability: Code written with testability in mind
