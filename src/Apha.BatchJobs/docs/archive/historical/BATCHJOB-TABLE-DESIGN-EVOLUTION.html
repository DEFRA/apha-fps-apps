BatchJobs Table Design Evolution and Locking Recommendation

Captures the design journey from the original 4-table model to the current implementation, including the rationale for introducing fps.job_lock.

Scope: This document focuses on execution tracking and concurrency control for jobs such as RecreateSummaries and MABArchive.

1. Original Table Design (Baseline)

The original model introduced four operational tables for job definition, status standardization, queueing, and run audit trail.

Table Purpose Exact Columns (Original Design) Design Intention
tbljobmaster Job definitions jobid, jobname, frequency, note, timetolive One row per job type (for example, MABArchive, RecreateSummaries).
tbljobstatus Status catalog statusid, jobid, status Controlled list of transitions used by queue and log tables.
tbljobqueue Execution instance header jobqueueid, jobid, statusid, startdatetime, enddatetime, errormessage Single row per run containing latest status and runtime metadata.
tbljobqueue_log Execution audit trail jobqueuelogid, jobqueueid, statusid, performedby, logtime, note Chronological state history for each queue row.
Conclusion on sufficiency: These four tables are sufficient for tracking and audit. They are not sufficient by themselves to guarantee single-run concurrency per job.

2. Current Implementation Mapping

The implementation retains the same conceptual model in the fps schema and adds practical fields used by API/UI trigger flow.

Source of truth for local schema: current EF Core mapping in BatchJobsDbContext. The exact columns below are taken from the local code configuration.
Concept Implemented Table Exact Columns (Current Local) Notes
Job master fps.job_master jobid, jobname, frequency, note, timetolive, created_at, updated_at Equivalent to baseline tbljobmaster.
Status master fps.job_status statusid, jobid, status, created_at Equivalent to baseline tbljobstatus.
Queue header fps.job_queue jobqueueid, jobexecutionid, jobid, statusid, requestedby, startdatetime, enddatetime, errormessage, created_at, updated_at Extended to support external trigger correlation and requester identity (requestedby).
Queue logs fps.job_queue_log jobqueuelogid, jobqueueid, statusid, performedby, logtime, note Equivalent audit design.
Concurrency lock fps.job_lock lock_id, job_name, acquired_at, expires_at, jobqueueid, is_active Added to enforce one active run per job atomically.

2.1 Additional Runtime Identity Clarification

  • jobExecutionId: external correlation id generated by API/scheduler trigger path.
  • jobQueueId: internal per-run worker identity generated in orchestrator.

These identifiers improve traceability but do not enforce mutual exclusion by themselves.

2.2 Current Local Constraint and Index Notes

  • fps.job_master: unique index on jobname.
  • fps.job_status: unique index on (jobid, status).
  • fps.job_queue: unique index on jobexecutionid, index on requestedby.
  • fps.job_lock: indexes on job_name, (job_name, is_active), and expires_at.

2A. Original vs Current: Mismatch and Justification Matrix

This section explicitly compares the original design text to the current implementation and explains why each deviation was introduced.

Change Area Original Design Current Implementation Why the Change Was Made
Table naming convention tbljobmaster, tbljobstatus, tbljobqueue, tbljobqueue_log fps.job_master, fps.job_status, fps.job_queue, fps.job_queue_log Aligned with PostgreSQL schema-qualified naming and existing FPS operational style for consistency, migration hygiene, and easier DBA operations.
Audit timestamps on master/queue tables Not explicitly present in the original 4-table definitions. Added created_at/updated_at on job_master and job_queue, and created_at on job_status. Required for operational auditability, troubleshooting, and support diagnostics without relying only on queue logs.
External correlation id on queue jobqueueid treated as run correlation id. jobqueueid retained as internal run id; added jobexecutionid (unique) for external API/UI correlation. Separates worker-owned runtime identity from caller-owned tracking identity so API status polling and user-visible traceability remain stable.
Requester identity capture No requester column in tbljobqueue. Added requestedby (NOT NULL) in fps.job_queue. Supports full audit chain (who requested what), authorization evidence, and easier incident triage for manual triggers.
Timezone precision Original text says timestamp. Implemented as timestamp with time zone for runtime time columns. Prevents ambiguity across environments/time zones and improves correctness for distributed systems and cloud operations.
Concurrency control model No dedicated lock table in original 4-table set. Added fps.job_lock with job_name, acquired_at, expires_at, jobqueueid, is_active. Original queue/status model tracks execution but cannot atomically prevent duplicate concurrent starts for the same job during race conditions.
Active-run uniqueness enforcement No explicit uniqueness rule for one active run per job. Lock repository acquires lock atomically using insert-conflict strategy and lock indexes. Guarantees one active instance per job name while allowing different jobs (for example, MABArchive + RecreateSummaries) to run in parallel.
Queue constraints/indexing FKs described at conceptual level. Added concrete indexes and constraints, including unique jobexecutionid and indexed requestedby. Improves query performance for status lookups and preserves correlation integrity in trigger/status APIs.
Queue log naming correction Review notes flagged underscore naming and final name as tbljobqueue_log. Implemented as fps.job_queue_log. Carries forward the same naming intent (underscore separation) within schema-qualified PostgreSQL naming standards.
Key justification summary: The original design was strong for execution tracking and auditing. The current implementation extends it for production-grade distributed triggering: identity separation (jobexecutionid vs jobqueueid), requester accountability (requestedby), explicit audit timestamps, and atomic concurrency safety (job_lock).

3. Why Duplicate Runs Can Still Happen Without Lock

Foreign keys and unique run ids validate relationships and uniqueness of each run record, but they do not express the rule: "only one active run per job name at a time".

3.1 Example Race (No Lock)

T0: Trigger A starts RecreateSummaries
T0+5ms: Trigger B starts RecreateSummaries

A checks queue for Running rows: none visible yet
B checks queue for Running rows: none visible yet

A inserts queue row with jobqueueid=A1, status=Running
B inserts queue row with jobqueueid=B1, status=Running

Result: two concurrent RecreateSummaries instances
Risk: overlapping instances may process the same dataset concurrently, causing duplicate writes, non-deterministic outcomes, lock contention, or deadlocks, depending on job step implementation.

4. Lock Table Introduction and Value

To enforce single active run per job atomically, the implementation introduces a dedicated lock table: fps.job_lock.

Table Purpose Important Fields Enforcement Pattern
fps.job_lock Distributed mutex per job job_name, jobqueueid, acquired_at, expires_at, is_active Atomic acquire via insert with conflict handling against active lock uniqueness.

4.1 Atomic Acquire Pattern

INSERT INTO fps.job_lock(acquired_at, expires_at, job_name, jobqueueid, is_active)
VALUES(now_utc, now_utc + timeout, 'RecreateSummaries', :jobqueueid, TRUE)
ON CONFLICT DO NOTHING;

rows_affected = 1 -> lock acquired -> execute
rows_affected = 0 -> another run active -> skip/reject

4.2 Why This Is Better Than Queue Status Check

  • Single atomic DB statement; no check-then-insert race window.
  • Explicit lock lifecycle separated from audit lifecycle.
  • Supports stale lock recovery using expires_at.

5. Job-Level Concurrency Behavior (Desired State)

Case Expected Behavior With Lock Without Lock

6. Final Recommendation

Keep the original four tables for execution definition, queueing, status, and audit, and retain fps.job_lock as a required concurrency-control table.

6.1 Recommended Canonical Set

  1. fps.job_master - job metadata
  2. fps.job_status - valid state catalog
  3. fps.job_queue - one row per run (latest state)
  4. fps.job_queue_log - state transition history
  5. fps.job_lock - one-active-run-per-job guard

6.2 Documentation Update Guidance

  • Present job_lock as an intentional architectural addition, not an accidental table.
  • Clarify that GUID-based correlation and locking solve different problems.
  • Record lock timeout policy and stale-lock cleanup behavior.
  • State expected concurrency rule explicitly: one active instance per job name.

7. Operational Scenarios (Happy Path to Worst Path)

The following scenarios document expected runtime behavior with current controls: API trigger acceptance, worker retries, lock acquisition, transaction rollback, and DLQ handling.

7.1 Happy Path (Single Click, Normal Startup, Success)

  1. User clicks RecreateSummaries once.
  2. Trigger API accepts request and publishes event.
  3. Worker container starts and orchestrator acquires fps.job_lock.
  4. Job execution row is created in fps.job_queue with status Running.
  5. All steps execute in one transaction and commit.
  6. Final job status updates to Completed and lock is released.
Outcome: one successful committed run, clean queue and queue-log history.

7.2 Step Failure Inside RecreateSummaries Transaction

  1. A mandatory or refresh step returns failure/throws exception.
  2. Orchestrator rolls back the entire transaction.
  3. No partial business data changes are committed.
  4. Job status updates to Failed; lock is released (or eventually expires if release path fails).
Outcome: run fails atomically; UI should show Failed + rollback message, not partial success.

7.3 Transient Failure with Retry (Try/Catch + Retry Policy)

  1. Worker/orchestrator encounters retryable infrastructure exception (for example timeout, network, DB transient).
  2. Configured retry policy applies delay/jitter and re-attempts within configured limits.
  3. If a later attempt succeeds, final status becomes Completed.
  4. If all attempts fail, final status becomes Failed and error is recorded.
Outcome: retries increase resilience without changing one-run-at-a-time lock semantics.

7.4 Trigger Accepted but Container Startup Delayed

  1. API accepts event, but ECS/container startup is delayed.
  2. UI/browser may be closed and reopened before worker starts.
  3. User may click trigger again, producing another accepted event.
  4. When workers start, lock ensures only one active execution runs; extra run is skipped at lock stage.
Outcome: execution safety is preserved, but duplicate accepted triggers can still occur pre-lock.

7.5 Lock Contention Scenario

  1. Two worker instances attempt the same job concurrently.
  2. First instance acquires lock and runs.
  3. Second instance cannot acquire lock and is marked Skipped (or equivalent non-run outcome).
Outcome: prevents concurrent duplicate execution of the same job while allowing different jobs in parallel.

7.6 Worst Path (Repeated Delivery Failure -> DLQ)

  1. Event delivery/start repeatedly fails (infra issue, permissions, task launch failures, etc.).
  2. Retries are exhausted by the messaging/dispatch layer.
  3. Message transitions to DLQ for manual/automated remediation.
  4. User-visible status should map to StartFailedDeliveryExhausted (or equivalent failure terminal state).
Outcome: no run is executed; incident response must inspect DLQ payload and replay/fix cause.

7.7 Worst Path (Worker Crashes Mid-Run)

  1. Worker acquires lock and starts execution.
  2. Worker crashes before clean lock release.
  3. Lock persists until expires_at; next run waits until expiry or cleanup.
Outcome: stale-lock timeout prevents permanent deadlock but can delay next valid run.

8. Best Practices and Recommendations

8.1 UI Behavior Recommendations

  • Default UI should display run-level status only: Accepted, Running, Completed, Failed, Timeout, DeliveryFailed.
  • If a run fails in-transaction, show explicit message: "Run failed and was fully rolled back; no partial data committed."
  • On page load, restore current in-flight state from API/server instead of resetting to a clickable default.
  • Disable trigger button when server reports active pending/running execution for the same job.

8.2 Trigger Deduplication Recommendations

  • Add server-side dedupe window (for example 5-10 minutes) keyed by job name + requester + business context.
  • Support idempotency key in trigger API requests and reject duplicate keys within TTL.
  • Expose a "latest accepted execution" endpoint so UI can rehydrate state after browser reopen.

8.2.1 Recommended Trigger API Contract

Include the following fields in trigger requests and responses for deterministic dedupe behavior:

  • Request: jobName, requestedBy, businessContext, optional idempotencyKey.
  • Computed server value: businessContextHash from normalized context payload.
  • Response: executionId, acceptedAtUtc, startupDeadlineUtc, status, isDuplicate, duplicateOfExecutionId.

8.2.2 Dedupe Decision Order (Server)

  1. Validate request and normalize business context (stable key ordering and trimming).
  2. If idempotencyKey is present, check key replay first within idempotency TTL.
  3. Then evaluate semantic dedupe window using jobName + requestedBy + businessContextHash.
  4. If duplicate found, return existing execution metadata; do not publish another trigger event.
  5. If no duplicate found, create new accepted execution and publish event once.

8.2.3 Suggested HTTP Status Behavior

  • 202 Accepted: new trigger accepted and event published.
  • 200 OK: duplicate replay detected; existing execution returned.
  • 409 Conflict: same idempotency key reused with different payload fingerprint.
  • 400 Bad Request: invalid business context or unsupported key format.

8.2.4 Time Windows and TTL Defaults

  • Semantic dedupe window: 5 minutes default, 10 minutes when startup delays are common.
  • Idempotency TTL: 24 hours default for manual UI-triggered operations.
  • Latest execution lookup horizon: at least dedupe window + expected startup SLA.

8.2.5 Latest Accepted Execution Endpoint

Provide a lightweight read API for UI state rehydration after refresh/browser reopen:

GET /api/trigger/latest?jobName=RecreateSummaries&requestedBy=jane.doe&contextHash=abc123
200 OK
{
  "executionId": "...",
  "status": "Accepted",
  "acceptedAtUtc": "2026-06-02T10:00:00Z",
  "startupDeadlineUtc": "2026-06-02T10:02:00Z",
  "workerProcessLaunched": false,

}

8.2.6 Suggested Persistence Model (Documentation-First)

To keep current execution tables stable, implement dedupe/idempotency in a separate trigger-intent store (new table or dedicated persistence model) rather than overloading fps.job_queue.

Field Type Purpose
intent_id UUID Primary key for trigger intent row
job_name text Batch job identifier
requested_by text Caller identity used in dedupe key

8.2.7 Concurrency and Race Condition Guardrails

  • Perform dedupe check and trigger-intent insert in one transaction.
  • Use unique index patterns to enforce idempotency and dedupe safety under parallel requests.
  • Keep worker lock flow unchanged; dedupe prevents duplicate accepted triggers before lock stage.

8.2.8 Two-Stage Insert Model (Explicit Clarification)

The recommendation is to keep two distinct inserts at different lifecycle stages, each solving a different problem. This is additive architecture, not a replacement of the current lock table behavior.

  1. Stage A (Trigger API, pre-worker): insert/update trigger-intent row for dedupe/idempotency.
  2. Stage B (Worker runtime): acquire/insert lock in fps.job_lock before execution.
Important: Stage A reduces duplicate accepted triggers; Stage B still enforces one-active-run execution safety.

8.3 Retry and DLQ Recommendations

  • Keep retry list strict to transient exceptions only (already aligned in orchestrator logic).
  • Instrument retry count, final error type, and elapsed retry window in logs/metrics.
  • Operationalize DLQ with runbook: root-cause classification, safe replay steps, and notification routing.

8.4 Step-Status Persistence Recommendation

  • For business UI only, extra step table is not required.
  • For support/engineering diagnostics, persist step telemetry in a dedicated table outside the business transaction, or rely on structured logs/APM traces.

9. Executive Summary (for Review Meetings)

The original design was correct for tracking, audit, and monitoring. As implementation matured, distributed runtime concurrency risk became explicit. The additional job_lock table closes that gap by enforcing single active run per job atomically, while still allowing different jobs to run in parallel. This is the latest recommended and implemented model.
