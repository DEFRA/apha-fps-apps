Updated for JobExecutionId external correlation + orchestrator-generated JobQueueId model (May 2026). Triggers must provide BATCH_JOB_EXECUTION_ID and BATCH_REQUESTED_BY. Canonical document: This HTML is now the single primary BatchJobs design and delivery document. Earlier standalone repository, DevOps, compliance, and implementation HTML pages have been retired to avoid duplication and drift.
Current Implementation Status (May 2026):
  • Worker generates jobQueueId internally at startup for runtime/DB identity.
    • The user interface must support secure, auditable initiation and monitoring of Batch Jobs. UI flows should align with the strict batch contract, including required context values such as jobExecutionId, userId, and yearContext where applicable.

Context: The worker/batch application already contains orchestration, locking, logging, execution control, status management, and job-specific execution logic. The decision here is only about the trigger/orchestration entry point.

2. Final Recommendation

Use API -> EventBridge -> ECS Task as the standard trigger model for manual/API-triggered batch jobs.

2.1 Single-Slide Summary (Presentation Shortcut)

Decision in one line: Keep API as a business-event publisher and move ECS runtime orchestration ownership to infrastructure via EventBridge target configuration.

6. Job Execution ID and Correlation

Since the API may not touch the database before the worker starts, the API can generate a jobExecutionId itself and include it in the event. This ID becomes the business-level correlation key.

API generates jobExecutionId -> API publishes EventBridge event -> API returns jobExecutionId to UI -> EventBridge invokes ECS worker task -> Worker receives jobExecutionId as env variable -> Worker creates/updates job status in DB -> UI polls status using jobExecutionId

If the UI polls before the worker inserts the row, the status API can return PendingStart / TriggerAccepted for that jobExecutionId.

6.1 JobExecutionId to JobQueueId Flow (Updated)

Clarification: jobExecutionId is API-generated correlation ID. jobQueueId is database/runtime execution row identity from fps.job_queue. Both should be linked once worker starts.

1) API receives trigger request 2) API generates jobExecutionId (GUID) and publishes EventBridge event 3) API returns TriggerAccepted + jobExecutionId to UI 4) Worker starts with BATCH_JOB_EXECUTION_ID=jobExecutionId 5) Worker inserts execution row in fps.job_queue - Worker/orchestrator generates jobQueueId (GUID) before lock acquisition - Row stores correlation/jobExecutionId 6) Worker and status APIs expose both IDs for traceability 7) UI continues polling by jobExecutionId (stable external key) - API may additionally return jobQueueId once available

6.1.2 Correlation Rule

  • External/UI/API correlation key: jobExecutionId.
  • Internal database/worker key: jobQueueId.
  • Every log line and status payload should include jobExecutionId; include jobQueueId once known.

6.1.3 Generation Ownership (Manual and Scheduled)

  • Manual runs (UI-triggered): API generates jobExecutionId, returns it to UI, and sends it to worker as BATCH_JOB_EXECUTION_ID.
  • Scheduled runs: Scheduler/triggering API generates jobExecutionId and sends it to worker as BATCH_JOB_EXECUTION_ID.
  • Worker behavior: uses incoming jobExecutionId as correlation id. If missing/invalid, worker generates a fallback GUID and uses that value for both correlation and execution tracking.
  • Target state: keep fallback for resilience in transition, then enforce caller-generated jobExecutionId in non-local environments.

8.2 API Code - Publish Event

using Amazon.EventBridge;
using Amazon.EventBridge.Model;
using System.Text.Json;

public async Task<string> TriggerBatchJobAsync(
    string jobName,
    string requestedBy,
    CancellationToken cancellationToken = default)
{
    ArgumentException.ThrowIfNullOrWhiteSpace(jobName);

    var jobExecutionId = Guid.NewGuid().ToString("N");

    var detail = JsonSerializer.Serialize(new
    {
        jobExecutionId,
        jobName,
        runMode = "Manual",
        requestedBy,
        requestedAtUtc = DateTime.UtcNow
    });

    var request = new PutEventsRequest
    {
        Entries =
        [
            new PutEventsRequestEntry
            {
                EventBusName = _configuration["EventBridge:EventBusName"] ?? "default",
                Source = _configuration["EventBridge:Source"] ?? "fps.api",
                DetailType = _configuration["EventBridge:DetailType"] ?? "BatchJob.TriggerRequested",
                Detail = detail
            }
        ]
    };

    var response = await _eventBridge.PutEventsAsync(request, cancellationToken);

    if (response.FailedEntryCount > 0)
    {
        var failureText = string.Join("; ", response.Entries
            .Where(e => !string.IsNullOrWhiteSpace(e.ErrorCode))
            .Select(e => $"{e.ErrorCode}: {e.ErrorMessage}"));

        throw new InvalidOperationException($"Failed to publish batch trigger event. {failureText}");
    }

    return jobExecutionId;
}

using Amazon.ECS;
using Amazon.ECS.Model;

public async Task<string> TriggerViaEcsAsync(string jobName, string requestedBy)
{
    var jobExecutionId = Guid.NewGuid().ToString("N");

    var response = await _ecs.RunTaskAsync(new RunTaskRequest
    {
        Cluster = _configuration["Ecs:ClusterArn"],
        TaskDefinition = _configuration["Ecs:TaskDefinitionArn"],
        LaunchType = LaunchType.FARGATE,
        NetworkConfiguration = new NetworkConfiguration
        {
            AwsvpcConfiguration = new AwsVpcConfiguration
            {
                Subnets = _configuration.GetSection("Ecs:Subnets").Get<List<string>>()!,
                SecurityGroups = _configuration.GetSection("Ecs:SecurityGroups").Get<List<string>>()!,
                AssignPublicIp = AssignPublicIp.DISABLED
            }
        },
        Overrides = new TaskOverride
        {
            ContainerOverrides =
            [
                new ContainerOverride
                {
                    Name = _configuration["Ecs:ContainerName"],
                    Environment =
                    [
                        new KeyValuePair { Name = "BATCH_JOB_EXECUTION_ID", Value = jobExecutionId },
                        new KeyValuePair { Name = "BATCH_JOB_NAME", Value = jobName },
                        new KeyValuePair { Name = "BATCH_RUN_MODE", Value = "Manual" },
                        new KeyValuePair { Name = "BATCH_REQUESTED_BY", Value = requestedBy }
                    ]
                }
            ]
        }
    });

    return response.Tasks.First().TaskArn;
}

8.4 Publish Reliability and Failure Contract

The API publish path uses bounded retry for transient EventBridge ingress failures and returns a deterministic 503 payload when publish is not accepted.

Behavior Current Contract
Transient publish handling Up to 3 attempts with exponential backoff and jitter for throttling/timeout/5xx style failures.
Request cancellation Cancellation token is respected and operation exits immediately when caller cancels.
Publish failure response API returns 503 ServiceUnavailable with machine-readable reasonCode.

8.5 Implemented Polling Endpoint for Option 2 (No New Lifecycle Table)

To avoid indefinite PendingStart without adding a new API lifecycle table, the API exposes an inference endpoint that combines:

  • jobExecutionId (from trigger response)
  • acceptedAtUtc (from trigger response)
  • Execution existence check in fps.job_queue
  • Timeout rule: acceptedAtUtc + timeoutSeconds + bufferSeconds
GET /api/batch-jobs/triggers/{jobExecutionId}/startup-status
    ?acceptedAtUtc=2026-05-08T10:12:30Z
    &timeoutSeconds=3600
    &bufferSeconds=120

Returned status is one of:

  • PendingStart (no queue row yet, still within timeout window)
  • StartFailedTimeoutLikely (no queue row after timeout window)
  • Running / Completed / Failed (queue row exists and worker status observed)
Current option-2 caveat: API does not programmatically query DLQ. StartFailedTimeoutLikely is an inference based on timeout + missing execution row, while DLQ alarms/operations remain infra-driven.

8.6 Failure Handling Approach (Publish Side vs ECS Startup)

Failure Point Detection API/Infra Response UI/Client Contract
Publish failure before EventBridge acceptance PutEvents exception or failed entry from AWS SDK. API retries bounded (3 attempts). On final failure returns 503 + reasonCode. Treat as not accepted; safe to retry trigger with same business intent.
Event accepted but ECS task/container does not start No execution row by startup deadline and/or DLQ signal from exhausted EventBridge target retries. Mark lifecycle as StartFailedTimeout (inferred) or StartFailedDeliveryExhausted (DLQ confirmed). Show startup failure state; allow retry and surface operator guidance.
Container started but application crashed early ECS task stop reason + worker logs + status row transitions. Status transitions to Failed with failure metadata persisted for troubleshooting. Show execution failed after start (not publish failure).

8.6.1 Recommended Retry Semantics

  • Publish-side failure: API-level retry only, because EventBridge never accepted the event.
  • Post-accept delivery failure: EventBridge target retry + DLQ path only, not API retry loop.
  • Startup timeout: one user/client retrigger action after deadline; avoid aggressive automatic retrigger storms.

8.6.2 Compact Failure Sequence (Review-Friendly)

Failure Path A: Publish-side failure (before EventBridge acceptance) UI -> API Trigger Endpoint -> PutEvents attempt #1/#2/#3 -> still failed -> API returns 503 + reasonCode=PublishTransientFailedAfterRetry -> UI shows "Not accepted" and offers retry Failure Path B: Event accepted, but ECS container fails to start UI -> API Trigger Endpoint -> PutEvents accepted (TriggerAccepted + jobExecutionId) -> EventBridge Rule/Target invokes ECS -> ECS startup fails (image pull/IAM/network/capacity) -> no worker-start signal by startupDeadlineUtc -> API projects StartFailedTimeout -> if DLQ evidence arrives: project StartFailedDeliveryExhausted -> UI shows startup failure with retry + operator diagnostics

Presenter tip: emphasize that Path A is producer-boundary reliability (API retries), while Path B is post-accept delivery reliability (EventBridge retry/DLQ + startup deadline projection).

11. End-to-End Reliability Flow and Settings

11.0 Ownership Boundary Clarification (PACT vs FPS vs Worker)

Important ownership model: PACT API and FPS API are separate trigger owners with separate UIs. Each API owns its own trigger lifecycle tracking and status projection. The worker domain remains execution-focused and is not the place for API-specific trigger lifecycle states.
Concern Owner Notes
Trigger accepted / pending startup / startup timeout / delivery exhausted PACT API or FPS API (independently) Stored and exposed from each API's own trigger lifecycle store.
EventBridge retry and DLQ routing Infra (per API event route) Each API flow should have clear routing ownership and DLQ handling.
Job execution runtime status once task starts Worker runtime/domain Worker remains responsible for running/completed/failed execution semantics.

11.1 Configured Reliability Boundaries

Boundary Configured Setting Intent
API -> EventBridge ingress API-side bounded transient retry: maxAttempts=3, exponential backoff + jitter. Handle throttling/timeouts/5xx before event acceptance.
EventBridge Rule -> ECS target Retry policy: MaximumRetryAttempts=24, MaximumEventAgeInSeconds=3600. Handle transient target invocation failures after EventBridge has accepted the event.
EventBridge Rule -> DLQ DeadLetterConfig enabled to SQS DLQ (for example batch-trigger-dlq). Capture events that could not be delivered to ECS target within retry window.
API failure response contract 503 with deterministic reasonCode. Allow UI/client to decide retry vs operator action consistently.
Important boundary rule: EventBridge target retry/DLQ only applies after EventBridge accepts the event. If PutEvents fails at API ingress, only API-side retry/handling applies.

11.2 End-to-End Sequence (Manual Trigger)

1) User triggers job from UI. 2) API validates request and running-state guard (400/404/409 paths if invalid). 3) API generates jobExecutionId. 4) API calls PutEvents to EventBridge. - If ingress transient failure: API retries up to 3 attempts. - If still failed: API returns 503 with reasonCode. 5) EventBridge accepts event and matches rule. 6) EventBridge invokes ECS RunTask target. - If target invocation transiently fails: EventBridge retries per policy. - If retries exhaust or event age exceeded: Event pushed to DLQ. 7) Worker container starts, reads env overrides. 8) API-side lifecycle tracker marks startup observed and projects Running based on worker/runtime signals. 9) Worker writes execution outcomes (Running/Completed/Failed) and logs with jobExecutionId. 10) UI polls its own API and renders lifecycle + execution state.

14. Final Design Summary

Final direction (2026):
  • Use EventBridge as the common trigger layer for API/manual jobs and scheduled jobs, with ECS Fargate as the worker execution runtime.
  • All triggers (API, UI, scheduled) should inject BATCH_JOB_EXECUTION_ID and BATCH_REQUESTED_BY (string).
  • Use BATCH_YEAR_CONTEXT for caller-scoped jobs such as RecreateSummaries. Scheduled MABArchive derives year internally from the execution date.

15. Additional Process and Governance Addendum

15.1.1 Legacy Manual Process

The existing FEC Price List update process is a manual, Excel-driven workflow. Data is extracted from database tables (tlkpTestReqmt for AGRUP and TestOrProduct for FEC) using scripts and pasted into an Excel workbook (PriceListsMaster.xlsx). The workbook is shared with business users, who update existing records and add new entries. The updated file is then processed using an ETL tool (FME Form), which generates SQL scripts for inserting and updating records along with corresponding rollback scripts. A summary of changes is validated by the business user before the relevant SQL scripts are manually executed against the database. This process involves multiple manual steps, external dependencies, and limited validation and control mechanisms.

Similarly, Staff rates and Animal rates are updated in bulk directly using the database by a single user. The user creates a temporary table in MS Access where new rates are updated, then, based on this temporary table, the main table is updated.

15.1.2 New System Approach

In the new system, users will not have direct access to the database to update rates. The following section describes the new, controlled process for bulk rate updates, ensuring improved validation, auditability, and security.

15.2.1 Overview

The MABArchive schema stores project budgeting, milestones/deliverables, and multi-year financial data summaries from FPS for management reporting. This job processes and loads FPS data from the current and previous calendar years to support financial year reporting into the MABArchive schema within the same PostgreSQL database. It runs weekly on weekdays at 8:00 PM, replacing a chain of legacy MSSQL stored procedures (sp_LoadFromFPS and its dependents) with a single managed .NET batch process hosted on AWS ECS Fargate.

15.2.2 Year Resolution Logic

MABArchive derives its year internally from the execution date in a single orchestrator method. The current month decides whether the primary year is the current calendar year or the previous calendar year, matching the legacy month-cutover behavior. The handler does not require caller-provided BATCH_YEAR_CONTEXT for scheduled MABArchive runs.

Related engineering trackers: MABArchive LINQ Conversion Tracker and MABArchive Unit Test Tracker.

15.2.3 Processing Steps

  • Full Load (primary year):
    • Rebuild FPS source totals in the source schema to ensure the load draws from up-to-date figures.
    • Delete existing archive data for that year (in dependency order across 24 tables).
    • Load fresh data from the FPS source schema into the corresponding archive tables (24 sequential INSERT-SELECT steps).
  • Partial Refresh (month <= 4 only, current year):
    • Delete and reload only the my_tlkpproject_all cross-reference table from source. No other archive tables are touched.

15.2.4 Transactional Guarantees

All processing runs inside a single database transaction. If any step fails, the entire run is rolled back, leaving the archive in its previous consistent state.

15.2.5 Concurrency Control

A database lock table prevents concurrent runs. If a second instance starts while one is already running, it exits immediately.

15.2.6 Failure Notification

On failure, an email notification is sent to the configured administrator with the CorrelationId (derived from jobExecutionId) and error details, enabling diagnosis via CloudWatch Logs. For runtime tracing, use jobExecutionId as the external key and jobQueueId as the internal execution key.

15.3.1 Overview

Recreate Summaries is a critical financial consolidation process that regenerates summary data for a specified accounting period in the FPS (Financial Planning System) and populates multiple summary tables in the database. It performs a complete refresh of the financial data hierarchy by first clearing out existing summary data through deletion, then systematically rebuilding all financial totals, staff time cost calculations, and project summaries from transactional data.

The process begins by removing and recreating FPS totals which aggregate financial information across projects, followed by ensuring all active projects are properly registered in the system through the insertion of any missing project records. It then proceeds to delete and recreate time cost calculations that determine staff costs based on staff hours and rates and subsequently handles project month casework data which tracks the detailed work performed on each project during specific periods.

The core financial summarisation occurs through a series of job month queries that calculate both single-period and cumulative financial metrics including costs, invoices, work-in-progress values, and milestone achievements for each project.

After completing the primary calculations, the process checks whether the specified period is locked for editing, and if the period remains open (unlocked), it refreshes three additional period-specific tables containing monthly output data, project subcontract information, and test cost calculations to ensure all Oracle integration data remains synchronised.

This comprehensive rebuild process ensures that all financial summaries, project costs, and revenue calculations are accurate and up to date for management reports and financial dashboards. This process provides an accurate, complete financial picture of each project for the specified period based on the most current transactional data available in the system.

15.3.2 Year Context Requirement

The year context (BATCH_YEAR_CONTEXT) is required for this process. It determines the accounting period for which all summary data is rebuilt. The year context must be injected by the caller (API, UI, or scheduler) and is strictly validated by the worker. This ensures that all calculations, deletions, and insertions are performed for the correct financial period, maintaining data integrity and supporting accurate reporting.

15.5 Testing Strategy and Plan for Batch Jobs

Testing Principle:
The BatchJobs solution is financially significant, calculation-heavy, and operationally critical. For that reason, the testing strategy must be intentionally exhaustive. The goal is not only to prove that jobs run, but to prove that they produce correct, repeatable, auditable outcomes under both normal and failure conditions.

  • Calculation Accuracy First: Priority must be given to validating financial calculations, summary regeneration logic, year-based processing, archive loading, and rate update outcomes against known-good baselines.
  • Regression Safety: Legacy SQL/stored procedure behavior being migrated into .NET must be regression-tested so the new implementation matches expected business outcomes.
  • End-to-End Confidence: Testing must cover UI/API initiation, approval workflows, EventBridge trigger publication, ECS worker execution, database side effects, status projection, notifications, and failure handling.
  • Repeatability: Test suites should be runnable repeatedly with deterministic seed data and expected outputs.
  • Production Risk Reduction: Every critical batch process should have enough automated coverage to reduce manual verification effort and lower the risk of financial or operational defects escaping to production.

Recommended Test Layers

  • Unit Tests: Validate domain rules, orchestration branching, year selection logic, approval gating logic, environment variable validation, and status transitions.
  • Repository and Database Integration Tests: Validate EF Core mappings, SQL behavior, transaction boundaries, lock handling, data deletion/recreation logic, and schema assumptions against PostgreSQL.
  • Parity Tests: Compare .NET orchestration and calculation outputs against legacy SQL/stored procedure expectations or approved baseline datasets.
  • API Integration Tests: Validate request handling, validation errors, approval flows, jobExecutionId generation, and EventBridge publish contract formation.
  • Infrastructure / Trigger Path Tests: Validate EventBridge to ECS triggering, environment variable mapping, schedule execution, DLQ behavior, and startup timeout handling.
  • End-to-End Functional Tests: Validate the full path from UI submission to API acceptance to worker execution to database results and surfaced status.
  • Non-Functional Tests: Include resilience, concurrency, rollback, recoverability, and operational monitoring validation for long-running or high-impact jobs.

Critical Coverage Expectations by Process

  • Calendar Year End: Test table copy logic, year creation, configuration-driven field updates, approval flow, and safe cutover behavior.
  • Re-Create Summary: Test full summary regeneration, period lock behavior, year-context handling, cumulative calculations, and downstream table refreshes.
  • Bulk Rate Updates: Test validation of uploaded or submitted rate changes, insert/update rules, auditability, rollback behavior, and downstream impact on derived calculations.
  • Mab Archive: Test year resolution logic, full-load versus partial-refresh paths, transaction rollback, dependency ordering, and archive consistency across all affected tables.

Test Data and Baseline Requirements

  • Create representative seed datasets covering multiple years, open and closed periods, active and inactive records, and mixed project/rate conditions.
  • Maintain approved baseline outputs for critical financial calculations so parity and regression checks are objective.
  • Include edge cases such as leap years, year-boundary cutovers, empty data sets, duplicate trigger attempts, invalid year context, and concurrent execution attempts.
  • Support anonymised production-like datasets where needed for confidence in calculation-heavy scenarios.

Release Gate Recommendation

No critical batch process should be promoted without successful automated test execution across unit, integration, and parity coverage for the touched area. For high-risk changes affecting calculations or year-based logic, a controlled business verification of output should also be part of the release gate.

15.15.1.5 jobExecutionId and jobQueueId Column Guidance

  • jobQueueId: Runtime and persistence primary key for execution rows. Stored in fps.job_queue.jobqueueid and referenced from fps.job_queue_log.jobqueueid.

  • Strict mode recommendation: Use jobQueueId as the database source of truth, and keep API correlation deterministic for traceability.
  • Indexing recommendation: Keep indexes on fps.job_queue(jobid, startdatetime) and status lookup columns used by polling/status endpoints.

15.17 Best Practice: Passing Context to Batch Jobs

Recommendation: Pass all required context values - such as BATCH_REQUESTED_BY, BATCH_YEAR_CONTEXT, BATCH_JOB_EXECUTION_ID, BATCH_JOB_NAME, etc. - as separate environment variables to the worker container.

  • This is the native and recommended pattern for AWS ECS, EventBridge, and containerized batch jobs.
  • It enables simple, language-agnostic access in the worker code (e.g., Environment.GetEnvironmentVariable in .NET).
  • It avoids the need for parsing composite objects or JSON strings.
  • It is transparent for debugging, logging, and operational visibility.
  • It aligns with AWS EventBridge input transformer and ECS task definition best practices.

Summary:
Always inject each required value as a separate environment variable. Do not combine into a single object or JSON string.

15.18 FPS Calendar Year End Process

The Calendar Year-End Process prepares the FPS database for the upcoming planning cycle by creating the required data records and enabling the FPS application for the next calendar year. During this process, a predefined set of scripts are executed to populate multiple database tables with records associated with the new FPS year.

This process is divided into two main steps:

  • Step 1 - New Calendar Year Data Setup Initiation & Approval
  • Step 2 - New Calendar Year Cutover

15.18.1 New Calendar Year Data Setup Initiation & Approval

Data Setup Initiation

An authorised user initiates the New Calendar Year process through the user interface. Prior to initiating the process, the user must provide the required configuration values or validate the existing configuration settings. Once the configuration is confirmed, the user submits the request for approval to proceed with the process.

Data Setup Approval and Preparation

An authorised approver receives the request to approve the initiation of the New Calendar Year process. The approver can either approve or reject the request. Upon approval, the system triggers the subsequent automated steps for data preparation and further processing. For data preparation, the application executes a set of SQL scripts to populate data in multiple tables with the next year identifier. The initiator should raise a new request on rejection or failure.
